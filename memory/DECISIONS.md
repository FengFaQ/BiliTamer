# 关键决策记录 / Decisions

> 只记「会影响以后改法」的取舍，以及**被否掉的方案**（避免下一版重走弯路）。
> 技术细节在 `PITFALLS.md`，这里记「为什么选这个方向」。

## D1. 独立维护：这是 FengFaQ/BiliTamer，不再跟随上游

* 决策：把上游 `mengwuzhuanshou/BiliTamer` @46505f7 作为历史基线，之后在本仓库独立演进。
* 理由：上游节奏与需求不一致；本次功能（倍速两项）经过独立审计与重构，需要自己的
  Release/发版节奏。
* 影响：升级上游功能要**手动**对比/挑选（`git diff 46505f7..upstream/main`），
  不要无脑 merge——上游混淆锚点与本仓可能有冲突。

## D2. 默认倍速：只在「起播」改参数，其余时刻零干预

* 决策：`SpeedHooks` 只 hook `eK1.q#setPlaySpeed(float)`，且**仅当调用栈里有 `onPrepared`**
  时替换入参；非起播（用户手动选档、宿主复位）一律原样放行。
* 被否掉的方案：v1.10.1 用「调用栈里有没有 `PlaySpeedManagerImpl`」判手动并跟随。
  6.7.1 dex 实证该类不在两条真实手动链路上 → 判据永远 false → 用户选档被静默改回配置值。
  教训见 `PITFALLS.md` §63。
* 被否掉的方案：hook 内核 `IjkMediaPlayer.setSpeed`。上层每次起播都会重算并覆盖，白改。
* 被否掉的方案：hook `R0(Z)F` 初值计算做兜底。R0 结果只会被 `onPrepared` 立刻喂给
  `setPlaySpeed`，没有绕过路径，多挂 = 多一个改写面。
* 收益：一条改写路径、无会话状态机、无线程共享状态；「跟随用户」靠「不拦」实现。

## D3. 倍速档位：后处理「档位表出口」的返回值，不碰静态字段/UI 适配器

* 决策：hook `com.bilibili.playerbizcommonv2.utils.B#a(MediaResource, Integer, boolean, int):ArrayList`
  的返回值，整表替换。
* 理由：这是宿主**唯一**的档位表构造点，至少 5 个调用点（旧 RecyclerView 面板、
  theseus Compose 面板、工具栏下拉菜单、播放设置面板…）都消费它；方法每次 `new ArrayList()`，
  无缓存；改返回值是纯后处理，宿主内部状态不动。
* 被否掉的方案：改静态字段 `B.a`（`static final List`）——各版本 ART 对 final 写入态度不一，
  且它还被 7 处**非菜单**消费者（半屏图标映射、长按 3 倍、投屏、画质联动等）读取，改了会破坏
  宿主的硬编码判定（`docs/speed-menu-anchor-6.7.1.md` §4.3）。
* 被否掉的方案：改 UI 适配器 / Compose 状态——两套消费端每版重写，且要改两处。

## D4. 元素类从宿主返回值反射取，不写死混淆名

* 决策：`itemCls = hostList.get(0).getClass()`，再取 `(F,Z)` 构造器；
  宿主类定位用「静态方法形状 + 同类静态 List 字段」四重校验，候选类名只作提示。
* 理由：R8 混淆名每版都换；返回值的元素类是**运行期事实**，天然抗漂移。
* 代价：空列表时只能退回候选名 + 形状校验；失败就 warn 并保持零干预。

## D5. 配置存储形态：整数百分比（默认倍速）+ 单行逗号字符串（档位表）

* 决策：`playback_speed_pct`（int，150=1.5x）、`playback_speed_list`（string，逗号分隔）。
* 理由：conf 的严格解析只认 boolean/int/单行字符串（`PITFALLS.md` §38），
  浮点键会让**整份副本**被丢弃；字符串列表已经是仓库里既有词表键的形态。
* 区间分两层：写入侧 25..300（设置页校验），读取侧兜底 25..400（兼容手写/旧 conf），
  行为边界恒 0.25..3.0。

## D6. 设置页控件落盘用 `commit()`（理由要写对）

* 决策：倍速两个控件用 `commit()` 后再 `persistAll(false)`。
* 正确理由：紧接着要把 SP 汇总成 conf 副本投递，同步写盘才能保证这份副本与界面一致，
  并避免「刚保存完进程被杀、磁盘还是旧值」。
* **不是**因为「apply() 会和 saveAll 赛跑读回旧值」——apply() 会先同步更新内存 mMap，
  同进程读到的必然是 new value。这个错误理由在 v1.10.1 注释里出现过，已纠正
  （审计 NIT-6）。

## D7. 验证诚实原则

* 决策：没有真机时，交付说明只写「静态 dex 实证 + 构建 + 纯逻辑单测」，
  并明确列出未上机验证的点。
* 理由：v1.10.0/v1.10.1 的教训——「构建通过 + 锚点在 dex 里」不等于「真机生效」，
  把前者写成后者会让用户按错误结论去排查。
